SHIFT.AI — MASTER PROJECT UNDERSTANDING / IMPLEMENTATION CONTEXT
File purpose: Give this entire file to an AI coding assistant before asking it to build, modify, debug, explain, or present the shift.AI project.

======================================================================
0. IMPORTANT INSTRUCTION TO THE AI READING THIS FILE
======================================================================

You are working on a hackathon project called shift.AI.

Do NOT treat shift.AI as a normal chatbot, a generic AI consultant, or a simple “recommend me an AI tool” application.

The core idea is different:

Most AI assistants jump directly from a user's request to a solution.

Example:
User: “I run a hospital and I need AI.”
Normal AI: “Use an AI chatbot, predictive analytics, automation, OCR, etc.”

shift.AI must NOT behave like that.

shift.AI first understands the organization, current workflow, people, software, pain points, constraints, documents, data readiness, budget, risk, and the actual business objective.

Only after understanding the current system does shift.AI decide:

1. AI is genuinely needed, OR
2. AI is not needed and the problem should be solved by:
   - workflow improvement,
   - process redesign,
   - staff/process changes,
   - automation without AI,
   - integration of existing software,
   - replacement/configuration of an existing tool,
   - better reporting/data collection,
   - training,
   - or another lower-cost solution.

If AI is justified, shift.AI should produce a practical AI solution blueprint, explain why it is needed, how it fits into the existing workflow, what it replaces or augments, what data is required, what risks exist, and how it can be implemented safely.

shift.AI is therefore an:
“AI Solution Architect + AI Readiness Consultant + Workflow Analyst + Red-Team Reviewer”
rather than only a chatbot.

This principle is the foundation of the entire product.

======================================================================
1. ONE-LINE PRODUCT DEFINITION
======================================================================

shift.AI is an AI decision and solution architecture platform that deeply understands a business or organization before recommending AI, verifies whether AI is actually necessary, designs the right solution when justified, and continuously stress-tests the proposed solution for risks, weaknesses, cost, feasibility, and unnecessary complexity.

======================================================================
2. THE PROBLEM shift.AI SOLVES
======================================================================

Current AI assistants have a common problem:

A user describes a requirement and the AI immediately gives recommendations.

The missing step is understanding the real environment in which that recommendation will be used.

Organizations often say:
- “We need AI.”
- “We need a chatbot.”
- “We need an AI receptionist.”
- “We need automation.”
- “We need predictive analytics.”
- “We need AI in our hospital.”
- “We need AI for customer support.”

But the actual problem may be something completely different.

For example:
- data may be stored badly,
- staff may be doing duplicate work,
- the current software may already have the needed feature,
- two systems may simply need integration,
- the workflow may be badly designed,
- a normal rules-based automation may be enough,
- employees may need training,
- the organization may not yet be AI-ready,
- AI may cost more than the problem is worth,
- AI may create privacy/security/compliance risk,
- the user may be trying to automate a symptom rather than fix the root cause.

Normal AI often optimizes for answering quickly.
shift.AI optimizes for recommending the right change.

This is the key differentiation.

======================================================================
3. PRODUCT PHILOSOPHY
======================================================================

shift.AI follows these rules:

RULE 1 — UNDERSTAND BEFORE RECOMMENDING
Never recommend an AI system immediately from the first user message unless enough context already exists.

RULE 2 — ASK ONLY USEFUL QUESTIONS
Questions must be dynamic and based on the user's organization, goal, current workflow, and missing information.
Do not show a huge generic questionnaire all at once.

RULE 3 — FIND THE ROOT CAUSE
The user's requested technology is not automatically the actual solution.

RULE 4 — AI IS NOT ALWAYS THE ANSWER
The system must be comfortable saying:
“You do not need AI for this.”

RULE 5 — RECOMMEND THE MINIMUM EFFECTIVE CHANGE
Prefer the simplest solution that creates measurable value.

RULE 6 — USE EXISTING SYSTEMS WHEN POSSIBLE
If the current tools can solve the problem through configuration, integration, or workflow changes, recommend that instead of unnecessary AI.

RULE 7 — EXPLAIN WHY
Every recommendation must include reasoning understandable by a business owner and enough technical depth for a developer.

RULE 8 — RED-TEAM THE SOLUTION
The first generated solution is not automatically accepted.
It must be attacked for failure modes, risk, feasibility, security, privacy, cost, hallucinations, bad assumptions, integration problems, and unnecessary complexity.

RULE 9 — ITERATIVELY IMPROVE
The final recommendation should reflect fixes suggested during the critique/red-team phase.

RULE 10 — BUILD TRUST
The product should feel like a professional consultant/architect, not a flashy generic AI chat application.

5. MAIN USER JOURNEY
======================================================================

The full user journey should work approximately like this.

STEP 1 — USER ARRIVES
The landing page explains that shift.AI does not blindly recommend AI.
It first understands the organization and identifies the real problem.

Primary action:
“Describe what you want to improve”

The user can begin in natural language.

Example:
“I own a hospital and I want an AI system to reduce patient waiting time.”

STEP 2 — INITIAL INTENT UNDERSTANDING
shift.AI identifies:
- organization/domain,
- stated goal,
- requested AI/technology if any,
- likely business process involved,
- important missing information,
- early assumptions that must be verified.

The system should not yet present a final solution.

STEP 3 — DISCOVERY / CONTEXT COLLECTION
shift.AI starts a guided conversation.

Possible information categories:
- organization type,
- team size,
- user/customer volume,
- current process,
- current software/tools,
- current data sources,
- what employees currently do manually,
- where time is lost,
- exact pain points,
- frequency of the problem,
- business impact,
- desired outcome,
- existing integrations,
- security/privacy requirements,
- budget,
- expected timeline,
- technical team availability,
- regulatory constraints,
- existing AI usage,
- data quality,
- deployment preference,
- success metrics.

Questions must be selected dynamically.

Do NOT require every field for every user.

STEP 4 — DOCUMENT / FILE UNDERSTANDING
The user can optionally upload supporting material such as:
- PDFs,
- Word documents,
- spreadsheets,
- text documents,
- exported workflows,
- SOPs,
- process documents,
- requirement documents,
- current system descriptions,
- architecture documents,
- screenshots/images where supported,
- reports,
- policies,
- sample forms,
- sample datasets where safe.

Uploaded material should be processed and converted into structured context.

The system should extract things such as:
- existing workflow,
- roles,
- tools,
- bottlenecks,
- repeated tasks,
- dependencies,
- data fields,
- current architecture,
- policies and restrictions,
- stated requirements,
- inconsistencies with the user's verbal description.

The system must not simply summarize the file.
It must use the file to improve its understanding of the business.

STEP 5 — CURRENT-STATE MODEL
Before proposing a solution, shift.AI should internally build a structured “current state” understanding.

Example structure:
- Business objective
- Current workflow
- People involved
- Current tools
- Data sources
- Pain points
- Root causes
- Constraints
- Risks
- Known unknowns
- AI readiness
- Success criteria

This structured context becomes the basis for later recommendations.

STEP 6 — ROOT-CAUSE ANALYSIS
shift.AI analyzes whether the user's requested AI feature actually addresses the root cause.

Example:
User says:
“We need an AI receptionist because calls are being missed.”

Possible finding:
The clinic already has an appointment platform with online booking but patients do not know about it and the phone routing is badly configured.

A better recommendation may be:
- fix call routing,
- enable missed-call callback,
- promote online booking,
- integrate notifications,
- measure call abandonment.

An AI voice agent may be considered later only if the remaining call volume justifies it.

STEP 7 — AI-NEED / SOLUTION DECISION
shift.AI classifies the recommended direction.

Possible decision types:

A. NO-AI SOLUTION
AI adds little value or creates unnecessary cost/risk.

B. PROCESS-FIRST
Fix process/data/software first. Re-evaluate AI later.

C. AUTOMATION WITHOUT AI
Use deterministic workflow automation, integrations, rules, or scripts.

D. EXISTING-SOFTWARE OPTIMIZATION
Configure or integrate tools the organization already has.

E. BUY / ADOPT EXISTING AI
A mature existing AI product solves the need better than building from scratch.

F. BUILD CUSTOM AI
A custom AI system is justified.

G. HYBRID
Use a mix of process redesign, standard automation, existing software, and AI.

This decision should be visible to the user.

STEP 8 — SOLUTION ARCHITECTURE
When AI or a technical solution is justified, generate a blueprint.

Blueprint should include:
- problem statement,
- current state,
- root cause,
- target state,
- why this solution was selected,
- why alternatives were rejected,
- high-level architecture,
- modules/components,
- AI model responsibility,
- non-AI logic,
- data flow,
- integrations,
- APIs,
- database/data storage,
- user roles,
- security considerations,
- human-in-the-loop points,
- fallback behavior,
- monitoring,
- implementation phases,
- required team/skills,
- estimated complexity,
- cost considerations,
- risks,
- measurable KPIs,
- MVP scope,
- future scope.

STEP 9 — RED TEAM / CRITIQUE
The proposed solution is attacked by a separate critical reasoning stage.

The red team should try to break the recommendation.

It should ask:
- Is AI really necessary?
- Is this over-engineered?
- Did we assume data exists?
- Is the data good enough?
- What happens when the model is wrong?
- Could this violate privacy?
- Could this expose sensitive data?
- Can the existing software already do this?
- Is a rules engine enough?
- Is the projected value realistic?
- Is there vendor lock-in?
- Is the solution affordable?
- Does the organization have the required technical capability?
- What is the failure mode?
- What should happen during API downtime?
- Can a human override the system?
- Is there an audit trail?
- Could hallucinations cause harm?
- Are permissions/roles properly defined?
- Is the workflow actually improved or only made more complex?
- Are there regulatory/compliance concerns?
- What assumptions are unverified?

STEP 10 — SOLUTION REFINEMENT
The architect stage receives the critique and modifies the solution.

The final answer should mention important changes that resulted from the red-team analysis.

Example:
“Initial idea: autonomous AI appointment scheduler.
Red-team finding: full autonomy creates scheduling and patient-safety risk.
Final design: AI gathers intent and suggests slots, but existing scheduling software remains the source of truth and confirms the booking.”

STEP 11 — FINAL REPORT / DECISION OUTPUT
The user receives a professional decision report rather than a generic chat answer.

Suggested sections:
1. What we understood
2. The real problem
3. Current-state summary
4. Key bottlenecks
5. AI readiness
6. Do you actually need AI?
7. Recommended solution
8. Why this recommendation
9. Proposed workflow
10. Proposed architecture
11. Required integrations
12. Data requirements
13. Red-team findings
14. Risk controls
15. Implementation roadmap
16. Estimated effort/complexity
17. Success metrics
18. Next steps

STEP 12 — CONTINUED ITERATION
The user can:
- answer more questions,
- change constraints,
- upload more documents,
- revise budget,
- revise the use case,
- ask for an MVP,
- ask for technical architecture,
- ask for implementation phases,
- ask for an executive version,
- ask for a developer version.

The current project context should persist within the session.

8. AI DECISION LOGIC
======================================================================

Do not base the final decision only on the LLM's unstructured opinion.

Use structured outputs.

Example internal assessment:

ai_need_score: 0-100
data_readiness_score: 0-100
process_readiness_score: 0-100
integration_readiness_score: 0-100
risk_score: 0-100
expected_value_score: 0-100
complexity_score: 0-100
confidence: 0-100

These values are decision aids, not fake scientific measurements.

The UI must explain what drives them.

Possible logic:
- high AI value + good readiness + manageable risk -> consider AI
- low AI value -> prefer non-AI solution
- high AI value + poor data/process readiness -> process-first roadmap
- high risk -> human-in-the-loop / limited automation / stronger controls
- existing system capability found -> configure/integrate before custom build

The final decision should come from structured evidence plus AI reasoning.

12. EXAMPLE HOSPITAL FLOW
======================================================================

This is a reference example, not a hard-coded application.

User:
“I need AI in my hospital to reduce waiting time.”

shift.AI first asks:
- Which waiting time: reception, appointment scheduling, billing, lab, doctor queue, pharmacy, emergency?
- What is the current patient journey?
- How are appointments scheduled?
- Which hospital management software is used?
- How many patients are handled daily?
- Is token/queue data available?
- Where do delays occur?
- Which steps are manual?
- Are staff entering the same information multiple times?
- What metrics are currently recorded?

Possible finding:
The major delay is not doctor diagnosis.
It is duplicate patient registration and manual transfer of appointment details between systems.

Potential recommendation:
Do NOT build a complex predictive AI system yet.
First:
- integrate registration and scheduling,
- use one patient ID,
- remove duplicate data entry,
- add queue visibility,
- collect timestamps.

After collecting reliable queue data, AI forecasting can later predict peak loads and staffing requirements.

This example clearly demonstrates shift.AI's philosophy.

13. RED TEAM DESIGN
======================================================================

The red-team feature must not be cosmetic.

It should produce structured critique.

Suggested critique schema:

{
  "assumptions": [],
  "unnecessary_ai": [],
  "technical_risks": [],
  "business_risks": [],
  "privacy_security_risks": [],
  "integration_risks": [],
  "data_risks": [],
  "failure_scenarios": [],
  "cost_concerns": [],
  "human_oversight_requirements": [],
  "recommended_changes": [],
  "severity": {}
}

The refinement stage must consume this critique.

Potential visible UI:
“Red-Team Review”
- 3 high-risk issues found
- 5 assumptions challenged
- 4 architecture improvements applied

Example:
Original:
AI automatically replies to patients and modifies appointments.

Critique:
AI can misunderstand urgency and scheduling constraints.

Refined:
AI handles FAQs and collects appointment intent.
Actual booking occurs through the existing scheduling system.
Critical messages are escalated to staff.
All AI actions are logged.

This is much more defensible in a hackathon demo.

19. API / ENVIRONMENT CONFIGURATION REQUIREMENT
======================================================================

A major implementation requirement:

The project should be able to start once the developer adds required API keys to .env files.

Do not hard-code secrets.

Provide:
frontend/.env.example
backend/.env.example

Example backend variables:

AI_PROVIDER=google
GOOGLE_API_KEY=
GOOGLE_MODEL=
DATABASE_URL=
APP_ENV=development
FRONTEND_URL=http://localhost:5173
MAX_UPLOAD_SIZE_MB=
SECRET_KEY=

Add any additional Google API variables only if the selected integration actually needs them.

If Google OAuth, Drive, Calendar, Gmail, Maps, Speech, or other Google services are used:
- isolate each integration in a service module,
- load credentials from environment variables,
- provide placeholders in .env.example,
- fail gracefully when an optional integration is not configured.

The developer should NOT need to rewrite application logic just to insert API credentials.

Expected workflow:
1. clone project,
2. install frontend dependencies,
3. install backend dependencies,
4. copy .env.example to .env,
5. add API keys,
6. start backend,
7. start frontend,
8. core application works.

Target:
After valid keys are inserted, approximately all core hackathon functionality should work without manual code edits.

23. SECURITY / TRUST REQUIREMENTS
======================================================================

Even for a hackathon MVP, show responsible engineering.

Must include:
- API keys only in environment variables,
- file type validation,
- file size limits,
- sanitized filenames,
- no executing uploaded files,
- uploaded content treated as untrusted,
- prompt-injection protection,
- error handling,
- logging without exposing secrets,
- input length limits,
- CORS configuration,
- server-side AI calls when secrets are required,
- clear fallback when provider API fails.

Where the domain is high-risk (e.g. healthcare):
- shift.AI is designing workflow/technology solutions, not replacing professionals,
- recommendations should include human oversight,
- avoid claiming clinical diagnosis functionality unless specifically designed and validated,
- surface privacy/security concerns.

39. ARCHITECTURAL PRINCIPLE: STATE > CHAT HISTORY

Do not rely only on sending the complete raw chat history back to the model.

project_context = {
  "organization": {...},
  "goal": {...},
  "current_workflow": [...],
  "tools": [...],
  "data": [...],
  "pain_points": [...],
  "constraints": [...],
  "facts": [...],
  "assumptions": [...],
  "unknowns": [...],
  "documents": [...],
  "readiness": {...}

Every discovery turn should update this state.

This makes the system:
- more reliable,
- easier to debug,
- cheaper to scale,
- easier to show in UI,
- easier to red-team,
- easier to generate reports from.

40. ARCHITECTURAL PRINCIPLE: EVIDENCE > ASSERTION
======================================================================

For important conclusions, store supporting evidence.

Example:

root_cause:
“Duplicate manual appointment entry”

evidence:
- user said reception manually copies bookings,
- uploaded SOP section says booking is re-entered,
- average processing time supplied by user is high.

Then recommendation:
“Integrate scheduling systems before introducing generative AI.”

This creates explainability.

- log actions,
- define rollback/fallback,
- keep existing authoritative systems as source of truth when appropriate.

Do not recommend fully autonomous AI simply because it sounds innovative.

If you remember only one thing, remember this:

shift.AI is NOT an AI that immediately solves the user's stated request.
